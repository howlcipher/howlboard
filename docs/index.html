Overview

HowlBoard is a full-stack task/board application used to test whether real applications can be built with HowlFrame.

It exists to turn language and runtime limitations into real application feedback. By strictly using HowlFrame for both the frontend JavaScript generation and the bytecode backend, it validates the platform's ability to handle CRUD, state mutations, deterministic transition rules, and browser interaction.

Dogfooding Evidence

HowlBoard has already materially improved HowlFrame. Building this application exposed real friction points and bugs in the compiler and runtime. These were fixed directly in HowlFrame.

  • HTML DOM Mutability: Discovered the JS backend lacked arbitrary HTML node injection and class toggling. Added set_html and toggle_class to HowlFrame's IR and JS backend.
  • Network & CORS: Exposed missing primitives for reading request methods and setting response headers. Added req_method and res_header to the HTTP server capabilities.
  • Type Checker Bugs: Encountered a compiler panic because try_let and parse_json were not registered in the JS backend checker. Fixed the AST walker.
  • Web Input: Discovered the inability to read DOM input text. Added the dom_value primitive to the JS backend.

The feedback loop is exactly: Application requirement → HowlFrame implementation → Compiler/runtime friction → Language/runtime improvement → Application continues.

Capability & Authority Model

HowlBoard implements strict, deterministic state transitions. A task in BACKLOG cannot jump directly to BLOCKED or DONE without going through READY and IN_PROGRESS.

For future AI involvement, the application acts as the enforcement boundary:

AI proposal
   ↓
HowlBoard deterministic policy (can_transition)
   ↓
ALLOW / DENY / REQUIRE_APPROVAL
   ↓
bounded state mutation

Build It

To run the live full-stack application on your own machine:

# 1. Clone repositories side-by-side
git clone https://github.com/howlcipher/howlframe.git
git clone https://github.com/howlcipher/howlboard.git

# 2. Build HowlFrame compiler
cd howlframe
go build -o ../howlboard/howlframe_bin howlframe.go

# 3. Build HowlBoard (compiles frontend and backend)
cd ../howlboard
make build

# 4. Run the backend
make run

# 5. In a separate terminal, serve the frontend
make run-frontend

Current Status

  • Working: Full frontend/backend compilation via HowlFrame, basic CRUD, explicit deterministic state transitions, native memory store.
  • Limitations: Deeply nested string concatenation in HowlFrame Lisp syntax is highly unergonomic and error-prone. Arrays/Lists are not easily handled in the REST payload without more complex AST loops.
  • Planned: Integration with LLM proposal systems, where the agent suggests updates that are bounded by the deterministic can_transition policy.
